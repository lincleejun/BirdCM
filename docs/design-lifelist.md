# BirdCM / 观羽: observations, life list and offline exploration

Implementation specification, 2026-11-18. Target: public `impl` branch (owner describes it as public main), iOS 17+, local desktop engine and web. Design only; no code changes or migrations have been executed. MUST denotes an acceptance requirement. Future proposals are exclusively in [ideas-ios.md](ideas-ios.md).

## 1. Decisions and existing contracts

Build one durable observation system on top of the existing history, not a second collection that starts empty. Keep every existing original, `Record.id`, timestamp, box, cached identification, display crop and shooting field. Installing over the existing bundle `cc.outman.birdcm` with Personal Team `3U353L39GB` MUST preserve the container. Never tell the owner to uninstall to upgrade.

Use SQLite on iOS through the existing system SQLite3 module (already used by `Rarity.swift`), and retain the engine's standard-library SQLite. Originals stay files. SQLite provides transactional changes, indexed aggregates and an inspectable exchange format without dependencies. The current one-JSON-per-photo store requires decoding roughly 0.5 MB of probability cache per bird to list history and cannot update aggregates atomically. SwiftData adds a different persistence/migration system and automatic CloudKit integration would not solve the free-team constraint. Do not use SwiftData, Core Data, a database package, a sync framework, a new routing package or a chart package.

Preserve the native navigation, system typography, pine/cream/amber tokens, 16 pt primary cards, 44 pt hit targets, 54 pt primary actions and crop/export rules in `ios/DESIGN.md`. Reference screenshots contribute only species-level photo grouping, calendar activity and intelligible summaries. Do not reproduce their profile composition, artwork, names, tiers, levels, experience points or completion rewards. The 11,172 denominator is a catalogue count, not a goal or a claimed count of Chinese names.

Inspected implementation contracts:

- `HistoryStore` currently reads all `History/*.json` with adjacent `<UUID>.photo`, excludes the folder from system backup, and saves each newly selected image as a new UUID. `Record.manual` means a hand-drawn box, **not** a species correction. `date` is identification time. `results` uses stringified box indices; `result` is the selected result and may be the only saved result in old files.
- iOS currently identifies bird 1, then others on selection; at most six crop pages are displayed. Unopened boxes have no species result. Retain this lazy inference; never treat all boxes as bird 1's species.
- `Confirm` currently uses 0.94 species/genus decisions plus range abstention; do not change model thresholds for this feature. The model's `rare` flag is a geo-prior warning, distinct from GBIF rarity.
- Desktop `scan`/`photo`/`correction`/`single`, `species_fix`, superseded scan history and `Store._write` are authoritative. Zero stars and rejected photo quality are not proof that a manually corrected bird was absent.
- `docs/prd-mobile.md` and early `docs/design.md` contain obsolete model-download and location proposals; current `ios/README.md`, `ios/DESIGN.md`, code and this spec govern this change. `ios/VALIDATION.md` records compilation, not proof that the reported UI failures are resolved.

## 2. Free-team delivery and backup, not sync

Apple's [iOS capability matrix](https://developer.apple.com/help/account/reference/supported-capabilities-ios/) has checks for ADP/ADEP and an empty free “Apple Developer” column for **all three**: iCloud CloudKit, iCloud documents, iCloud key-value storage. The HTML icon cells were checked because the text-only rendering drops the checks. Apple's [account overview](https://developer.apple.com/help/account/basics/about-your-developer-account) identifies a nonmember's Xcode account as a Personal Team and requires periodic reprovisioning. Therefore this release MUST NOT add iCloud entitlements, ubiquity containers, `NSUbiquitousKeyValueStore`, CloudKit or automatic iOS↔web sync.

What the owner gets now: local durable history, manual export/import of one portable file through Files, eBird CSV, and opt-in periodic **foreground** backup to a selected folder. Files can target iCloud Drive or another installed provider. This is ordinary user-granted document access, not an app-owned iCloud capability. Apple's [document-picker guide](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/DocumentPickerProgrammingGuide/AccessingDocuments/AccessingDocuments.html) explicitly distinguishes this from iCloud entitlement access; [directory access](https://developer.apple.com/documentation/uikit/providing-access-to-directories) documents persistent directory bookmarks.

Use `UIDocumentPickerViewController(forOpeningContentTypes: [.folder], asCopy: false)` for the backup destination. While accessing its scoped URL, save an iOS `.minimalBookmark`, resolve it on subsequent launches, balance `startAccessingSecurityScopedResource()` / `stopAccessingSecurityScopedResource()`, and coordinate provider writes with `NSFileCoordinator`. Do not use macOS-only bookmark entitlements/options. Handle stale bookmarks by renewing them; revoked access requests choosing the folder again, with local history unaffected. Some providers may not support persistent writes: show that limitation, keep manual export usable, and test both On My iPhone and iCloud Drive on the owner's phone.

Backup policy: off until a folder is chosen. When dirty, attempt after the next foreground activation if the last successful backup is ≥24 hours old (initial choice offers Backup now); coalesce saves and run one export off the main actor. Offer Backup now regardless of interval. Use dated `BirdCM-<UTC timestamp>-<UUID>.birdcm` files, retain the last three **successfully verified files created by this installation** in that folder; delete none until a new one verifies. Never replace an unfamiliar file. Stop before foreground time expires, leaving no claimed success. Show last local write/verification time, estimated bytes and error/retry state. No BGTask timer, silent periodic guarantee, server, conflict merge or file watching. “备份文件已写入；云端上传由文件提供方处理” is the success copy; never “已同步”. Cloud upload completion is not observable here.

Later, paid Apple Developer Program enrollment enables app iCloud capabilities. A later CloudKit adapter can map stable asset/subject IDs and explicit edits to a private database; it needs its own conflict/deletion design and tests. This release provides transactional read/write/export boundaries and stable identities, **not** a pretend SyncEngine or speculative network code. The local system remains usable when a future adapter fails.

## 3. Meaning of a sighting and every number

### 3.1 Evidence versus observation

A photo is immutable selected file bytes, identified by lowercase SHA-256 of the **whole original file**, streamed without decoding. Do not hash a thumbnail, filename, path, EXIF-free pixels or Photos local identifier. Identical bytes imported twice are one logical photo; a metadata rewrite or RAW/JPEG pair is different bytes and may be different evidence (daily grouping below still prevents inflated individuals). No perceptual hashing or automatic near-duplicate deletion.

A subject is one nonduplicate detected or hand-drawn box in that photo, with its own model result and optional human correction. Existing boxes are normalized upright-source `[x0,y0,x1,y1]`, top-left origin, not `[x,y,width,height]`. Preserve `DisplayCrop` as display geometry, separate from model cropping. Suppress detector duplicates with the existing `displaySubjects` overlap rules; a hand-drawn replacement replaces the selected subject, not all other birds. Offer Remove this subject for a false detection; original photo remains.

A **counted observation / 观察记录** is all eligible evidence of **one effective species × one effective local calendar day × one place bucket**, across photos, sources and scans. This conservative grouping is identical on both platforms. It deliberately underestimates repeat encounters at a site; it does not claim individually tracked birds or a scientific census. Different species in one photo yield different observations. Repeated visits on that day in the same bucket stay one observation; outing splitting is a later proposal.

Place buckets are deterministic:

- Actual point: `p:<floor(lat*100)>:<floor(lon*100)>`, using degrees in `[-90,90]` / `[-180,180]`; normalize +180 to -180 and clamp +90 to the last latitude cell (8999). About 1 km at the equator, not a fixed distance. Labels/source do not affect grouping. Use these explicit bins on both platforms, not Python/Swift's differing decimal-rounding behavior.
- Chosen administrative region: `r:<ISO code>`; representative coordinates never become actual observation coordinates.
- None: `none`. All unknown-place evidence of a species on that day merges conservatively. Explain “地点未知的同日记录合并，可能低估次数”; do not invent a GPS point or split by filename.

`group_key` is compact UTF-8 JSON array `["obs-v1", scientific, local_day, place_key]` with no whitespace. This encoding avoids delimiter collisions. Never embed a translated name or a rarity tier in identity.

### 3.2 Eligibility and quantities

| State | Counted in species, observations and estimated quantity? | Display |
|---|---|---|
| Model reports `level=species`, a catalogue species key, `clear != false`, not explicitly excluded | Yes; label 自动识别 | Model confidence remains the actual score; no extra user-save step |
| Human picks a species | Yes, even if model abstained/rejected/low clarity | 已人工更正; never invent 100% probability |
| Human sets 不确定; model genus/uncertain; unknown catalogue key; unclassified box | No | 待确认 with reason, original candidates and correction action |
| No detected/hand-drawn bird | No | 未找到鸟; retained in photo history, separate from pending subjects |
| Excluded subject or deleted photo | No | Immediately removed from aggregates |

Model auto-species and human corrections both count, because the owner requested automatic records. Show their provenance and a filter for 人工更正; do not call auto-species human-verified. Candidate top-1 alone never counts. Genus remains searchable in pending history, never a species tile or a fraction of a species. A legacy unresolved scientific key is preserved as pending, not silently mapped to a new taxon.

Each eligible subject defaults to count estimate 1. A subject's “数量” editor accepts integer 1–999998 or Reset to automatic; useful for a single hand-drawn flock box. Users can exclude an incorrect frame/box separately; zero is not an accepted count. Per photo/species count is the **sum** of its eligible subject estimates, after overlap deduplication. Observation estimate is the **maximum** photo/species count among its photos, not their sum. A group-level “本次观察数量” edit overrides the maximum; reset removes that override. Display “估计数量” everywhere, with “同日同地点取单张最大值；可能重复见到同一只鸟”. An override below the visible frame maximum is allowed after an inline explanation that it is the user's estimate. The range cap also matches eBird's numeric limit.

Examples: one frame has two confirmed Elegant Tern boxes → 1 observation, 2 estimated birds, 1 species, 1 photo. Three hundred such frames at the same place/day → still 1 observation and estimate 2, 300 photos. One confirmed tern plus one unclassified box → estimate 1 and one pending subject; there is no basis for assigning both to the tern. Provide “识别其余 n 只” to process remaining boxes serially with visible progress/cancel; keep each successful result on cancellation, no surprise background inference. More than six boxes are accessible through an “其他主体” list from Original, even though the six-page pager limit stays. Unprocessed boxes remain pending.

### 3.3 Aggregate definitions

- Species / 已见鸟种 = distinct effective eligible scientific keys.
- Observations / 观察记录 = distinct group keys.
- Estimated quantity / 估计数量 = sum of group estimates; never “unique individuals”. Daily repeats across dates can be the same individual.
- Photos / 照片 = distinct active asset hashes, including pending/no-bird history; species photo totals count distinct supporting hashes, so the sum across species can exceed the library photo total.
- Pending = number of active unresolved subjects; also show number of affected photos. No-bird photos are counted separately.
- Active days = distinct eligible `local_day`; identification/import dates do not create capture activity if capture date exists.
- First seen / 新种 = minimum eligible local-day for that species over **all time**. Every observation on that first day gets the badge; do not choose an arbitrary point within a day whose timezone may be unknown. Tie photo cover by local wall time then hash then subject ID. Importing an older photo moves the badge backward. In a period's “新种” total count distinct species whose first day falls in that period.
- This month/year = Gregorian calendar month/year of “today” in device/browser local zone, applied to stored local calendar days, with the actual range written on screen. Past periods selectable. All time includes everything, including dates in the future with a warning badge (do not silently drop them). Week begins Monday in the activity calendar.
- Rare observations = a counted group's applicable GBIF tier is 1 罕见 or 2 少见 at its **observed place and month**, not current home/month. Show 本地罕见 / 本地少见, never rarity-as-a-prize. Threatened = IUCN VU/EN/CR, separately; NT is not threatened, EX/EW are shown by their real labels. Unknown/zero records are not rare; zero is 无记录. A group containing two points in the same place bin can have differing region hits: evaluate each supporting photo, flag the group rare if any supporting eligible evidence has tier 1/2, expose each context, and do not fabricate a single uniform label.
- Rarity summaries count **observations** in disjoint buckets: 罕见, 少见, 不常见, 常见, 无记录, unavailable. For a mixed-context group take the minimum known tier (0 stays 无记录); unavailable only if none known. The Rare filter above remains “any tier 1/2”, so show its count independently rather than claiming those buckets equal that filter. Threatened species count is distinct species. No tier progress denominator is meaningful globally because tiers vary by place/month.

Re-identification updates existing logical evidence; same bytes do not create another observation/photo. A new identification may change model species, but cannot erase human correction, subject count, exclusion or group-count edits. Match redetected subjects greedily by descending IoU ≥0.5 (ties old ID then new index), one-to-one. Unmatched old subjects with human edits keep their IDs, are assigned unused ordinals after the new box ordinals, and remain explicit pending “需核对主体对应”, excluded from totals until the user attaches them to a new box or confirms the old box remains valid; retain their raw data. Unmatched unedited old subjects retire. Never copy a correction to a different bird silently. For an explicit hand-drawn replacement of the selected box keep its subject ID and edits; add-box makes a new ID. Pure location re-ranking uses saved visual vectors and leaves IDs/boxes unchanged. Missing vectors expose the current reselect/re-identify path, not a hidden model run.

Place/date edits regroup evidence transactionally. Group override keys do not migrate automatically to a different day/place/species; retain dormant edits, show “原观察数量更正未套用到新分组”, and offer entering a new estimate. If a group becomes empty, its count override has no statistical effect. Deleting a photo tombstones its canonical record and all byte-identical legacy aliases, then recomputes affected groups and first-seen values. Explain that the original in Photos/on disk is untouched. Keep a tombstone until explicit local cleanup; restoring a deleted photo by deliberately importing/selecting its bytes requires Restore confirmation. No new sightings are made by reopening, sorting, crop export, background removal or photo saving.

## 4. Time, place and dynamic labels

Store camera wall-clock time separately from any absolute instant. Parse EXIF `DateTimeOriginal`, subseconds and `OffsetTimeOriginal` strictly; use `Shooting.takenAt`, `timeOffset`, `photoPlace`, and preserve all `fields`. `local_day` is the valid capture string's Gregorian date component, independent of device timezone. With EXIF offset, preserve offset minutes and derive UTC; with no offset keep UTC NULL and show “照片未记录时区，按相机日期统计”. Do not infer historical timezone from today's device zone, a reverse-geocoder or longitude. Date-only imports are allowed with precision `day`; unknown time stays unknown.

If capture date is absent/invalid, freeze local wall time and timezone offset at **first identification**, `date_source=identified`; mark “拍摄日期缺失，按首次识别日期统计”. For old records with no capture date and no saved offset, migration uses the device zone at migration to render `Record.date` once and marks `identified_legacy_zone`; never claim that was the capture zone. Keep the original identification UTC instant in all cases. Subsequent re-identification/import must not move this fallback. A user may edit capture date/time and optional offset (`date_source=user`), with Reset to photo metadata restoring EXIF or the original frozen fallback. No new timezone database/dependency is required.

Initial effective place = valid photo GPS, else explicitly chosen home/map/device/region place, else none. Location permission is on explicit Locate tap only. A **result-level** user change can override GPS (existing contract); retain original GPS and offer Use photo location. Record `place_source=photo|map|device|region|none`, optional user override, precision and label. Region-only choices store their exact ISO code; their lat/lon representative is only a prior input, never a pin/CSV coordinate. Resolve actual points with the existing `Rarity.regionAt` algorithm once per point/table-version cache; no second polygon resolver in views. In desktop, use the same global-table algorithm (port/reuse the global reader); the present three-country `rarity.py` lookup cannot be assumed to understand the global file. If only the older table is installed, support it truthfully and show global coverage unavailable; do not download another table at runtime.

Persist raw species keys, time/place facts, counts and provenance. Names, IUCN, GBIF rarity, first-seen and period totals are read-time derivations. Never use `Identification.rarity`, cached Chinese names or `rare` as an immutable truth in the new views, result headers, search, saved crop captions or exports. Query a read-only catalogue/rarity service independent of `Engine` (so browsing does not load BioCLIP). Scientific name + `taxonomy_version=avilist-2026` is the portable species key; the rarity table's integer IDs/matrix indices are **not** stable IDs. Re-label all three names using current resources. A future taxonomic split needs an explicit alias migration; no automatic guess.

Bundled resources actually available: `names.tsv` has scientific/English/Chinese/genus/family (the loader requires ≥5 columns); `zh-names.json` refreshes Chinese. Chinese is absent for 59 species per NOTICE; show English and “暂无中文名”. No order column is guaranteed: include family/genus filters, **omit order**. The global rarity schema is `species(id,scientific,iucn)`, `regions(id,code,country,level,name_en,name_zh)`, `months(region_id,month,records,n_species,source_id,coverage)`, `counts(region_id,month,species_id,n,tier)`, `shapes(...)`, `meta(key,value)`; verified against the test database and referenced global builder. It contains no prose, photographs or taxonomy family/order. Follow `months.source_id` and country fallback, report `coverage=country` as 按全国数据估计; NULL source means 数据不足, not zero abundance. Cache labels by resource SHA, species, point/region and month; clear on resource change. `hideIUCN`, `BIRDCM_IUCN=0` and stripped builds must hide IUCN from all reads, filters, CSV/comments and exchange display snapshots alike; raw originals and immutable legacy recovery payloads remain untouched (inert archival provenance, never the source of a displayed IUCN badge). See [NOTICE.md](../NOTICE.md) for unresolved IUCN redistribution and geomodel licence statements; this design does not resolve them.

## 5. Exact iOS persistence, v1

Keep Application Support/History and its original paths; add `library.sqlite` inside it. Do not create a parallel user library. Before migration `PRAGMA user_version=0`; after success set 1. Fresh databases start at 1. `ll_meta('format')='birdcm-local-ios'`; unknown higher versions open no writer and offer a compatible-build/export recovery message. Use WAL, foreign_keys=ON, busy_timeout=5000; one serial actor owns the writing connection and short transactions; readers use separate read transactions. Never run `Rarity.db` concurrently across arbitrary tasks without its own serialization.

DDL (all times ending `_utc` are RFC3339 UTC with milliseconds, text; JSON is UTF-8 JSON text, nullable only where stated; numeric geometry is REAL):

```sql
CREATE TABLE ll_meta(key TEXT PRIMARY KEY, value TEXT NOT NULL);
CREATE TABLE ll_asset(
 hash TEXT PRIMARY KEY CHECK(length(hash)=64), byte_count INTEGER NOT NULL,
 mime TEXT NOT NULL, relative_path TEXT, width INTEGER, height INTEGER,
 shooting_json TEXT NOT NULL, missing INTEGER NOT NULL DEFAULT 0 CHECK(missing IN(0,1))
);
CREATE TABLE ll_record(
 id TEXT PRIMARY KEY, asset_hash TEXT NOT NULL REFERENCES ll_asset(hash),
 canonical INTEGER NOT NULL CHECK(canonical IN(0,1)),
 first_identified_utc TEXT NOT NULL, identified_utc TEXT NOT NULL, updated_utc TEXT NOT NULL,
 deleted_utc TEXT, origin TEXT NOT NULL, legacy_json TEXT,
 capture_wall TEXT, capture_offset_min INTEGER, capture_utc TEXT,
 date_precision TEXT NOT NULL CHECK(date_precision IN('second','day')),
 fallback_wall TEXT NOT NULL, fallback_offset_min INTEGER NOT NULL,
 date_source TEXT NOT NULL CHECK(date_source IN('photo','identified','identified_legacy_zone','user')),
 local_day TEXT NOT NULL, date_edit_json TEXT,
 lat REAL, lon REAL, place_label TEXT, place_source TEXT NOT NULL,
 region_code TEXT, place_edit_json TEXT,
 payload_json TEXT NOT NULL, revision INTEGER NOT NULL DEFAULT 1,
 CHECK((lat IS NULL AND lon IS NULL) OR
       (lat BETWEEN -90 AND 90 AND lon BETWEEN -180 AND 180))
);
CREATE UNIQUE INDEX ll_one_photo ON ll_record(asset_hash) WHERE canonical=1;
CREATE INDEX ll_record_day ON ll_record(local_day,asset_hash) WHERE canonical=1 AND deleted_utc IS NULL;
CREATE TABLE ll_subject(
 id TEXT PRIMARY KEY, record_id TEXT NOT NULL REFERENCES ll_record(id), ordinal INTEGER NOT NULL,
 x0 REAL NOT NULL,y0 REAL NOT NULL,x1 REAL NOT NULL,y1 REAL NOT NULL,
 crop_json TEXT, model_level TEXT NOT NULL, model_key TEXT, model_json TEXT,
 correction_state TEXT NOT NULL DEFAULT 'none'
   CHECK(correction_state IN('none','species','uncertain')),
 corrected_key TEXT, corrected_utc TEXT,
 count_edit INTEGER CHECK(count_edit BETWEEN 1 AND 999998),
 excluded INTEGER NOT NULL DEFAULT 0 CHECK(excluded IN(0,1)),
 retired INTEGER NOT NULL DEFAULT 0 CHECK(retired IN(0,1)),
 needs_match INTEGER NOT NULL DEFAULT 0 CHECK(needs_match IN(0,1)),
 updated_utc TEXT NOT NULL,
 CHECK(0<=x0 AND x0<x1 AND x1<=1 AND 0<=y0 AND y0<y1 AND y1<=1),
 CHECK((correction_state='species' AND corrected_key IS NOT NULL) OR
       (correction_state!='species' AND corrected_key IS NULL))
);
CREATE UNIQUE INDEX ll_subject_ordinal ON ll_subject(record_id,ordinal) WHERE retired=0;
CREATE INDEX ll_subject_record ON ll_subject(record_id);
CREATE INDEX ll_subject_species ON ll_subject(model_key,corrected_key) WHERE retired=0 AND excluded=0;
CREATE TABLE ll_group_edit(
 group_key TEXT PRIMARY KEY, count_edit INTEGER NOT NULL CHECK(count_edit BETWEEN 1 AND 999998),
 updated_utc TEXT NOT NULL
);
CREATE TABLE ll_legacy_issue(
 filename TEXT PRIMARY KEY, raw_json BLOB, photo_path TEXT, error TEXT NOT NULL
);
```

`origin` is `ios|import`; UUIDs are lowercase standard hyphenated UUID strings. `model_level=unclassified|species|genus|uncertain|unresolved`; `model_key` is only a scientific species/genus key actually named at that level. `model_json` preserves complete Identification including visual cache for that bird. `payload_json` preserves the complete current `Record` compatibility payload (selected bird, boxes, shooting, diagnostics etc.); field-specific columns/subject rows are authoritative after migration, and the store's compatibility decoder overlays them on reads. Writes update them together in one transaction; no UI writes the JSON side files. `legacy_json` preserves the original bytes-as-UTF8 string once and is never reinterpreted as a new authoritative store. `shooting_json` holds original EXIF facts, not result overrides. `date_edit_json` / `place_edit_json` hold NULL or the user's raw edit; effective columns are reproducible projections. Region-only lat/lon columns are NULL (its representative may remain in raw Place JSON). Validate all enums, JSON shape, finite coordinates, valid Gregorian `local_day`, monotonic revision, width/height, and normalized rectangles in the store API. Additional silent columns are not part of v1.

Store API boundaries: list paginated photo summaries; get full record/subject; upsert identification by hash; correct/reset species; edit/reset date/place/count; exclude subject; delete/restore photo; read aggregate snapshot; export/import archive. Mutations return the new revision and affected day/species keys. Use `expected_revision` for editors; stale edits show Reload and keep user input, never last-writer overwrite. Counts update after commit via one shared change notification. A future adapter may use these operations; no parallel user-observation database is allowed.

Effective subject = nonretired, nonexcluded, `needs_match=0`, belonging to canonical, nondeleted record. Resolve correction first, else model as §3. A normal SQL view can expose this join; aggregate in SQL by day/place/species, then label only the returned page. Initially no persisted summary cache on iOS: 10k evidence rows are small. Add one only after the performance acceptance fails, with deterministic rebuild and resource-version invalidation. Derived `place_key` can be calculated in the query/helper; it is not a new raw fact.

### 5.1 Migration and crash recovery

1. On upgrade, show a nonblocking-to-explanation “正在整理旧记录” screen with progress and free-space/error state; disable mutations until migration completes. Never call `HistoryStore.all()` on the main actor. Enumerate old JSON names and preserve unreadable files; do not reset a failed store to empty. Hash old `.photo` files in chunks, parse one JSON at a time, validate within a staging transaction/database. Use a deterministic manifest of filenames, SHA and record IDs for retry.
2. Import every decodable `Record.id` exactly. For each box make deterministic subject UUID from SHA-256 of `legacy subject / Record.id / index` (first 16 bytes, UUID version/variant bits set consistently on both platforms). For each `results[index]` use its result; otherwise only selected index may use `result`. Others are unclassified. Empty boxes retain a photo-only record. Preserve all raw fields; do not infer a species from history search's top-five matches.
3. Same hash in several old records: retain every UUID/payload as aliases. Freeze first_identified_utc and the no-capture fallback from the earliest identification among those aliases, not from the newest canonical result. Canonical is greatest `(Record.date, id)`; it supplies the active snapshot only. Surface duplicate legacy aliases under that photo's “旧识别版本”, explicitly “同一照片，只统计一次”. Do not merge differing historic boxes/results silently; users may inspect and explicitly restore an alias as canonical. Duplicate originals can stay at old paths until verified cleanup. `ll_asset.relative_path` uses the canonical's existing file; no original needs moving/transcoding.
4. Missing/corrupt originals: retain record and parsed facts with a namespaced deterministic placeholder asset hash `sha256('missing legacy photo/'+id)` and `missing=1`; show unavailable media, never synthesize bytes or count hash as a real content digest for cross-library dedup. Keep previously named eligible evidence counted, flagged “原图不可用”; its facts still exist. Malformed JSON goes to `ll_legacy_issue` with raw bytes/path and a visible recovery item, not discarded. It cannot enter statistics until repaired. Invalid boxes are retained in the raw payload and recovery list; do not clamp them into invented evidence.
5. Transactionally verify record-ID set, original-byte digests, all field mappings, aliases, unresolved counts and `PRAGMA integrity_check` / foreign_key_check. Only then set user_version=1 and migration-complete manifest; atomically install the DB and switch HistoryStore to that database. Interrupted migration retries from the manifest/staging without duplicating anything. If validation detects unexpected loss or an inconsistent mapping (beyond explicitly recorded recovery issues), leave old files readable through a read-only recovery view and allow exporting the untouched legacy files; do not mark complete.
6. Keep old JSON sidecars as read-only migration recovery files until a full verified portable backup exists and the owner explicitly chooses Free migration recovery space. Do not reread them into live history on relaunch. Their presence is not a second live store. A migration never deletes an original. New original writes stage a file, verify hash, rename into `assets/<hash>.photo`, commit DB reference, and clean unreferenced staged files after crashes; never commit a reference before file durability. Existing legacy file paths remain valid.

Use complete-until-first-user-authentication file protection. Remove the old blanket backup exclusion for irreplaceable live DB/originals (old directory flag must be reset); exclude only thumbnails, temp exports and redundant probability/cache files if actually separate. Ordinary OS backup availability depends on device settings and is not our promised backup. Do not retain all originals in RAM. On disk full, read-only mode preserves old store, retry is possible, no migration cleanup runs. Keep bundle ID, team and application support path unchanged; sign/install over, never delete the app to “fix” provisioning.

## 6. iOS interaction contract

Use a native four-item TabView, each with its own NavigationStack and preserved scroll/filter state. Launch to 识别; an identification result pushes on the initiating tab. Switching tabs preserves an unfinished correction/editor; no swipe paging between tabs. Map/calendar drilldowns keep the selected period; species pages default to the invoking scope and offer All records. Settings is a toolbar gear sheet from all four roots, not a fifth “我的” tab. Back returns to the source/filter/scroll position. Cross-tab “开始识别” selects 识别.

| Tab (SF Symbol) | First screen and navigation | Empty/offline behavior |
|---|---|---|
| 识别 (`camera.viewfinder`) | Existing product mark; compact current place summary and Locate / Map / offline region picker; primary 从相册选择, secondary 拍照. Latest three logical photo records and 查看全部 → 记录/照片. Show model readiness without blocking the other tabs. Result retains crop/original pager, metadata, save/share; add 更正鸟种 and 数量 for selected subject near name. | No history: one invitation to choose/take a bird photo. ## 7. Desktop engine and web

Keep engine photo rows and images where they are; a life list is a **derived index**, never a second copied scan/photo history. Add a rebuildable `ll_evidence` table in the same database, one row per normalized current source subject, plus hash identity cache and user group edits. Prefix all additive names; existing scan migrations remain intact. Engine's `PRAGMA user_version` is currently unused: set 1 for this additive library schema; store `ll_meta('derivation_version')='1'`, `generation` (integer string) and `dirty` (`0|1`). Do not overwrite a future higher version.

```sql
CREATE TABLE ll_meta(key TEXT PRIMARY KEY,value TEXT NOT NULL);
CREATE TABLE ll_hash(
 path TEXT NOT NULL,size INTEGER NOT NULL,mtime_ns INTEGER NOT NULL,
 hash TEXT NOT NULL, first_identified_utc TEXT NOT NULL,
 fallback_wall TEXT NOT NULL,fallback_offset_min INTEGER NOT NULL,
 PRIMARY KEY(path,size,mtime_ns)
);
CREATE INDEX ll_hash_digest ON ll_hash(hash);
CREATE TABLE ll_evidence(
 source_kind TEXT NOT NULL CHECK(source_kind IN('photo','single','import')),
 source_id TEXT NOT NULL, subject_id TEXT NOT NULL, asset_hash TEXT NOT NULL,
 species_key TEXT, level TEXT NOT NULL, provenance TEXT NOT NULL,
 local_day TEXT NOT NULL, capture_wall TEXT, capture_offset_min INTEGER,
 date_source TEXT NOT NULL, identified_utc TEXT NOT NULL,
 lat REAL,lon REAL,region_code TEXT,place_label TEXT,place_source TEXT NOT NULL,
 place_key TEXT NOT NULL, count_estimate INTEGER NOT NULL,
 box_json TEXT,crop_json TEXT,eligible INTEGER NOT NULL,updated_utc TEXT NOT NULL,
 PRIMARY KEY(source_kind,source_id,subject_id)
);
CREATE INDEX ll_evidence_group ON ll_evidence(eligible,species_key,local_day,place_key);
CREATE INDEX ll_evidence_asset ON ll_evidence(asset_hash);
CREATE TABLE ll_group_edit(
 group_key TEXT PRIMARY KEY,count_edit INTEGER NOT NULL CHECK(count_edit BETWEEN 1 AND 999998),
 updated_utc TEXT NOT NULL
);
CREATE TABLE ll_subject_edit(
 asset_hash TEXT NOT NULL,subject_id TEXT NOT NULL,edit_json TEXT NOT NULL,
 updated_utc TEXT NOT NULL,PRIMARY KEY(asset_hash,subject_id)
);
```

`ll_evidence` has facts only, no original bytes, copied result/visual JSON, names or rarity labels. It is disposable. Join `source_kind/source_id` to original `photo`/`single` (or imported records) to open details/media. Hash cache is computed lazily off the inference worker, hashing same file descriptor with before/after stat; changed files retry, unavailable files keep cached digest or a namespaced unresolved key and flag media unavailable. The first hashed appearance freezes first_identified_utc/fallback_wall/offset in ll_hash; every later path signature for that hash copies the earliest saved values, so no-date re-scans cannot move an observation to a later month. Backfill existing files from the earliest identification timestamp available in their source records (scan.created_at or single.created_at), with a one-time migration-zone flag when the historical offset was not saved; keep these identity facts when the derived index is dropped. No new parallel SQLite writer: all index/edit commits, dirty flags and existing result/correction transactions go through `Store._write`. A background reader can prepare rows, then writer swaps one complete generation transaction; readers see old or new generation, never half a rebuild. A source mutation marks dirty within its existing transaction. On process restart rebuild if dirty; UI reports 更新统计中 and generation, never silently shows new mutations with stale aggregates. For correctness prefer one whole rebuild after a completed scan before premature incremental optimization; coalesce correction/single changes. No model re-inference during derivation.

Source selection is exact:

1. Canonical folder is resolved absolute path, same as scan creation; folder scope key is `(folder, recursive)`. Choose the **highest scan ID in state completed** for each scope, not the newest in-progress/failed scan. If none completed exclude that scope from committed statistics and show pending status. A re-scan atomically replaces that scope when complete; older completed scans remain in normal scan history. Rescanned removed files disappear from life list, as this is a projection of current scans, not an archival assertion of every past scan.
2. Include done photo results of chosen completed scans regardless of stars. Read full per-box results (`slim_row` drops species data and must not be used here). Only subject box falls back to photo-level `result.species`/burst `species_fix`; never assign one photo-level species to all boxes. Other species-qualified boxes contribute independently; unresolved/rejected clarity gates follow §3. Explicit manual corrections outrank rejected status.
3. Overlay live `correction(path,size,mtime_ns)` before burst consensus/model for its selected subject; explicit NULL correction means pending. Existing burst/same scope corrections already write target rows: consume those, don't expand them again. Preserve existing photo-level correction behavior; new other-box/count/exclusion/date/place edits use `ll_subject_edit` validated JSON (same edit fields/states as iOS) keyed stable hash/subject identity. New changes in Results/Single correction UI must mirror the correction into that durable subject edit; legacy correction is fallback only. Stable desktop subject IDs derive hash + normalized box serialized with six decimal places; on re-detection use §3 matching to carry edited IDs. Persist these stable edited IDs in edit JSON with original box to match; never use current selection index as correction identity.
4. Include successful singles and their per-box results/corrections. Existing `single.correction` is an explicit override on the stored selected subject, not every box; migration binds it to that subject ID before the user switches subjects. A photo also present in a scan counts once by asset hash. Cross-scope/single overlap: choose one model snapshot per hash, ranked imported explicit edits > single explicit edits > scan explicit edits > otherwise newest result timestamp (use scan.created_at if no per-result time), ties source kind then numeric source ID. Conflicting explicit edits are not resolved by guessing: mark conflicting subject pending and offer choose-source UI; keep all provenance. No duplicate per-photo quantity from joining two scans. Daily grouping still collapses burst frames of different hashes.
5. Group eligible rows by §3 and compute max single-frame estimate, then group override. Never sum burst photos or use burst_group as a proxy for distinct individuals. No all-time source is selected just because its rows remain in SQLite.

For archive imports use the same core `ll_asset`/`ll_record`/`ll_subject` schema as §5 (names do not conflict with desktop derivative tables); set origin=import, original paths inside engine's managed import folder. Native engine scans remain solely in their existing tables. Imported records are authoritative **only for files explicitly imported**, included as source_kind=import, not copies manufactured from native scans. Import maps to a native subject edit when an existing native hash/box matches; preserve imported raw payload in the import record as provenance but exclude duplicate active evidence. Every import/rebuild can reconstruct its source mapping from those IDs/hashes. Desktop never deletes or changes originals in scanned folders; deleted/missing external files are represented honestly.

## 8. One portable single-file format and eBird CSV

Choose a **SQLite archive**, extension `.birdcm`, MIME `application/vnd.birdcm.archive`, format version 1, not a copied live database and not a Photos-only/metadata-only backup. Why: built-in SQLite on both platforms supports streaming large original BLOBs and read transactions; JSON with base64 grows originals by a third and typical Codable/JSON decoders materialize the whole archive. No ZIP library, JSON interchange variant or iOS↔web network sync.

Archive SQLite has `PRAGMA application_id=1112101441` (decimal, constant for this format), user_version=1, DELETE journal mode, no WAL sidecars/triggers/views/extensions. Tables are **exactly** `ll_asset`, `ll_record`, `ll_subject`, `ll_group_edit`, `ll_legacy_issue` from §5 plus:

```sql
CREATE TABLE archive_meta(key TEXT PRIMARY KEY,value TEXT NOT NULL);
CREATE TABLE archive_blob(
 hash TEXT PRIMARY KEY REFERENCES ll_asset(hash), original BLOB NOT NULL
);
```

`archive_meta` mandatory keys: `format=birdcm-archive`, `version=1`, `archive_id=<UUID>`, `library_id=<persistent installation UUID>`, `created_utc`, `producer=ios|desktop`, `taxonomy=avilist-2026`, `scope=full|selection`, `record_count`, `asset_count`, `subject_count`; `resource_versions` is a JSON object of catalogue/rarity SHA. Those versions explain derivation but bundled tables/models/name catalogues are **not** in the archive. Legacy/model payloads may contain historic cached names or labels; preserve them as inert provenance, never authoritative labels, and generate no extra display-label snapshot. Apply IUCN hiding to all projected/export display fields; do not rewrite immutable legacy recovery bytes. `ll_record.origin` retains source provenance (`ios|import|desktop` allowed in archive), UUIDs retained. All original media once per hash in archive_blob, missing assets explicitly absent with missing=1; no path authority (`relative_path=NULL`, legacy issue photo_path reduced to safe basename). `shooting_json`, payload/model JSON and legacy JSON preserve facts/caches; desktop builds portable record payloads from selected authoritative raw source results, not UI slim results. Export all current native hashes once with stable record UUIDs derived from `desktop native record / asset_hash` (independent of rescan ID) and stable subject IDs; include aliases from real stored history, never every superseded scan as active records. Original user filenames may be optional payload metadata; absolute paths/bookmarks/session tokens never exported. Build desktop portable payloads from the known result fields and strip source path/cache-path keys recursively; do not dump scan rows or event logs. Preserve source provenance as IDs and safe basenames. iOS Record payloads contain no absolute path authority; preserve their bytes/fields as specified. Export warning states exact location and original photographs are included and file is not encrypted; share only by explicit Files/Share action.

The versioned logical field contract is §5; readers ignore unknown **optional JSON** fields but reject unknown schema versions. Required-table/column whitelist, size/count checks and integrity/foreign-key check are mandatory. Never execute schema SQL found in a file; open read-only with extensions disabled, trusted_schema off where supported, query expected tables only, bound reads. Verify hash and byte_count of every original using incremental BLOB I/O and a bounded buffer, valid JSON/boxes/enums/canonical uniqueness; require a checked staging copy, not a live provider URL. Reject SQL objects outside the whitelist and original hash/blob mismatches. Missing-photo placeholders may only reference missing=1 with no blob. Show expected storage cost before apply; no giant allocation. On iOS keep picker scope only while copying to sandbox then release; on desktop upload to bounded disk staging rather than memory.

Export obtains one consistent raw-fact read snapshot, streams blobs into a new archive, verifies/reopens, closes before Files export. Do not copy live `library.sqlite` while WAL is active. Block physical deletion of referenced media for that snapshot until it ends. Cancel/full disk cleans staged file, original untouched. Format doesn't include thumbnails/derived aggregates/reproducible rarity or names. A full backup includes archived legacy bytes/issues and tombstones; selection export explicitly marks scope and is not a full restore backup.

Import defaults to Merge preview: new photos, identical photos, changed fields, conflicting edits, missing originals, pending subjects, and total sizes. Same library/UUID/revision with identical facts is no-op; same hashes dedup photos independent of source UUID. Never replace a correction automatically with a model result. Conflicting human edits/date/place/count are presented grouped by photo with Keep local / Use file (default local); apply selected result atomically, retain losing raw source as a legacy/provenance alias. Do not use wall-clock last-write-wins between devices. Imported tombstones do not delete local records in Merge; preview them and keep local unless explicitly chosen. Repeated import is idempotent. Imports restore dates/offsets as saved, never parse them in current timezone. A full archive offers Restore (replace library) only after a destructive confirmation, automatic local safety export and full validation. Selection archive cannot replace a full library. Use staging DB/files then atomic switch/transaction; failed/cancelled import leaves current library and source media unchanged. Native desktop scan source tables are never wiped by Restore: Restore replaces managed/import library and library edits, then rebuilds from still-existing native scans; preview this explicitly. For an empty desktop installation restore equals the archive semantically. iOS full export→wipe→restore must reproduce the complete raw state, original bytes, IDs, edits and resulting metrics (not file byte order/WAL/cache timestamps).

### 8.1 eBird Record Format on iOS

Reuse the **column/validation rules and golden fixtures** from `engine/birdcm/ebird.py`, not generic CSVEncoder behavior. Bundle existing AviList→Clements `ebird-names.csv` + attribution; no new taxonomy download. From current life-list scope show preview grouped by effective local day/place and species. Only eligible species by default; genus/pending excluded and their number explained. Mapping unavailable → show warning and allow deselection/manual eBird Fix Species later; never silently substitute a species. Export is a file for manual upload, not an eBird submission/API integration. Source: [eBird upload documentation](https://support.ebird.org/en/support/solutions/articles/48000907878-upload-spreadsheet-data-to-ebird).

Exactly 19 comma-separated fields, no header, no quotes anywhere, LF newline including trailing newline; UTF-8; at most 1,000,000 encoded bytes. `clean()` replaces double quotes, commas and line breaks/whitespace as desktop does, using the same field limits `[128,64,64,6,4000,254,12,12,10,5,3,2,16,4,4,1,8,8,4000]`. Columns: Clements English name, genus, species epithet, count, species comments, location name, latitude, longitude, MM/dd/yyyy date, HH:mm local start, state, country, protocol, observer count, minutes, complete Y/N, miles, acres, checklist comments. Scientific name split at first space as desktop does; unknown mapping is surfaced before export. State/country rules from existing `place_codes`; actual points resolve via same region lookup, region-only/no-place have blank coordinates (eBird Fix Locations needed). Nonempty location fallback “BirdCM location”. Coordinates format five decimals; pole clamp follows desktop's valid eBird coordinate range.

Default protocol Incidental, complete=N, observer/time/distance/area effort fields blank, count **X** even if internal estimate is 2. User can opt to Use estimates or edit each checklist/species count 1–999998 or X. Comment explains “From BirdCM photo review; not a complete count” and flags fallback capture dates. Require review acceptance for any fallback-date row; offer exclude such rows. Wall start time unknown → blank, not 00:00. Stationary is optional only when user deliberately selects it and supplies/reviews duration/observer values; inferred span of photos is not actual effort. Do not expose Stationary as a default fast path. Oversize file yields an actionable choose fewer dates/species message, no partial silent CSV. Adapt desktop life-list export to this normalized checklist grouping and shared fixtures; keep its existing scan exporter contract and tests. All time/place and daily maximum rules in this document apply to the new life-list export, while desktop's 19 field rules remain unchanged.

## 9. Performance, size, privacy and implementation boundaries

Acceptance budgets, measured on iPhone 15 with release build and synthetic 10,000 photos / 30,000 subjects, excluding originals from the metadata timing workload: first tab responsive ≤1 s cold after migration, cached list/filter/summary ≤250 ms p95, name results ≤100 ms after debounce, first species page ≤300 ms excluding lazy image decode. These are targets to measure, not existing claims. UI browsing must not wait for full model integrity scan/load; keep models lazy until identification, and Geo separately lazy on exploration. List page size50, thumbnail long edge120, disk thumbnail cache max100 MiB with LRU and excluded-from-backup. Decoded thumbnail memory budget24 MiB; one active crop ≤1200 px, one source-size export at a time, no model vectors in list queries. Added browsing memory target ≤80 MiB above idle; measure separately from existing BioCLIP peak. Do not promise existing whole-app memory from this delta.

For 10k evidence rows, raw-fact query/aggregation is cheap; lazy-load images, model JSON, original EXIF blobs, shape lookup labels, yearly heat map, map clustering and geo likelihood. Use prepared statements/transactions, indexed pagination; no launch-time regeneration of every crop, label or prior. Initial migration/hash/export progress is cancellable or safely resumable, never block main thread. Stream originals/hash/BLOB transfer with ≤1 MiB buffers. Keep archive staging space estimate (originals + metadata + safety backup when replacing); leave current library usable if insufficient disk. Originals dominate storage; expose exact bytes plus cache/recovery size and explicit cache clearing. Adding this feature MUST add ≤5 MiB to the ~698 MiB unsigned app baseline (small code, eBird name map); add no new model/media pack. Record actual bytes, cold timing and peak memory rather than estimating a pass.

All persisted points, filenames and photos private by default; no analytics, account, upload, public checklist or automatic permission request. Bundled-only identification/catalogue/rarity/likelihood; maps/browser links/Files providers can use network only on the user-initiated surface. No remote species photos, descriptions or audio scraping. Never log full coordinates or user filenames in public test artifacts. Repository fixtures use invented dates/coordinates/observations and existing documented CC0 photos only. Owner-store migration rehearsal uses a private copy outside Git, and evidence reports aggregate success counts only. No tests or screenshots use the reference apps' artwork as BirdCM assets.

## 11. Independently shippable build order

1. **Protect existing data:** serial SQLite store, private-copy migration/recovery, stable hash/subject IDs, compatibility history reader; current UI still works. Ship only after migration, fault and install-over acceptance. Add portable full backup/restore here so the next stages can be tried safely.
2. **Make facts editable:** selected-subject manual species correction, date/place/count/exclusion, corrected export captions and raw read-time names/rarity. Ship with legacy UI and focused flows; stats are not exposed before this prerequisite.
3. **Expose the library:** four native tab roots, records species/photo/pending and species page, full catalogue search; move settings/history and fix reachability/clipping. Camera and Vision fallbacks verified in this step. No empty placeholder future tab is shipped: Statistics initially has the working scoped summary/list and Exploration the working catalogue.
4. **Complete statistics/exploration:** month/year/all metrics, exact fixture, rare/IUCN, first-seen, calendar, MapKit and place/month likelihood/unseen list. Add eBird CSV and foreground folder backup. Ship against performance/accessibility/screenshot gates, no cloud entitlement.
5. **Desktop parity:** additive derived index, normalized corrections/source rules, APIs/web views/Leaflet, archive exchange and eBird shared fixtures; single-writer, rescan and cross-platform round trips accepted. iOS remains independently useful if this step follows later.

All scope decisions above have defaults. Owner-only choices do not block baseline implementation: whether to allow future public/social sharing or online hotspot services; which future proposal to prioritize; and whether/when to join the paid programme and resolve model/IUCN redistribution before distribution beyond personal builds. No implementer should reinterpret those future choices as permission to add an account, scrape media or upload observations now.
